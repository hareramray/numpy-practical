Step 1 · Basic slicing shares data

Writing to a view edits the original

original = np.arange(6)
view = original[1:4]
independent = original[1:4].copy()
view[0] = 99
print("Original:", original)
print("Independent copy:", independent)
assert np.shares_memory(original, view)
assert not np.shares_memory(original, independent)
assert original[1] == 99

Original: [ 0 99  2  3  4  5]
Independent copy: [1 2 3]

A slice is a view

original[1:4] points into the same data buffer.

.copy() is independent

New storage, so later writes do not leak across.

shares_memory checks

True when two arrays overlap in memory.

NumPy course · 11 Copies and views

3

A view is a new array object that refers to an existing data buffer. Basic slicing with start, stop and step normally produces a view, so view[0] = 99 writes into the same memory as original[1], and printing original shows 99 in position 1. The .copy() call allocates new storage, so independent still holds [1 2 3]. np.shares_memory answers the question directly and is the right tool when you are unsure. Try it: modify independent, for example independent[0] = -1, and confirm that original stays unchanged.

Step 2 · Advanced indexing and strides

Fancy indexing copies

a = np.arange(12, dtype=np.int64).reshape(3, 4)
selected = a[[0, 2]]
selected[0, 0] = -100
assert a[0, 0] == 0
print("Original strides:", a.strides)
print("Transpose strides:", a.T.strides)
print("C contiguous:", a.flags.c_contiguous,
      a.T.flags.c_contiguous)

Original strides: (32, 8)
Transpose strides: (8, 32)
C contiguous: True False

a[[0, 2]] is new data

Integer-array and Boolean reads copy, so a[0, 0] stays 0.

Strides are byte jumps

(32, 8): 32 bytes to the next row, 8 to the next column.

.T swaps the strides

Same bytes, new steps (8, 32), and no longer C-contiguous.

NumPy course · 11 Copies and views

5

Advanced indexing, meaning an integer array like a[[0, 2]] or a Boolean mask, cannot be described as a regular step through memory, so reading it returns a copy. Changing selected therefore leaves a untouched, which the assert proves. Assignment is different: a[mask] = value writes directly into a. That is why chained indexing such as a[mask][0] = 5 silently does nothing to a: the first indexing step already made a copy. Strides are the number of bytes to jump to move one step along each axis. Each int64 is 8 bytes and each row has 4 of them, so moving down a row jumps 32 bytes. The transpose simply swaps the strides to (8, 32) without moving any values, which is why it is no longer C-contiguous.

6

The top row is the real memory: one flat buffer of twelve 8-byte integers, with each cell's byte offset underneath. Both arrays below are just different ways of walking it. For a, shaped (3, 4), the next column is the next cell, 8 bytes on, shown in blue, and the next row starts 4 cells later, 32 bytes on, shown in orange. So a.strides is (32, 8). The transpose a.T shows the same numbers turned on their side, but no byte moved: NumPy only swapped the strides to (8, 32). Now moving along a row of a.T jumps 32 bytes, so its rows are not laid out one after another, and c_contiguous is False. Try it: compare np.shares_memory(a, a.T.reshape(-1)) with np.shares_memory(a, a.reshape(-1)). The second is True, because a is contiguous and reshape can return a view. The first is False, because flattening a.T in row order needs the bytes in a different order, so reshape must copy.

Use this table as a prediction checklist. Basic slices and transposes are views because they can be described with new strides over the same buffer. Integer-array and Boolean indexing return copies when reading, but assignment through them, as in a[mask] = value, writes into the original. Avoid chained indexing when you mean to modify the original. flatten always copies; ravel returns a view when the layout allows it, which it does for the contiguous a in the notebook, where shares_memory is True. reshape behaves like ravel: it may need a copy for other layouts, so inspect with np.shares_memory rather than assume.

Step 3 · Memory mapping

Read a file through a memory map

with TemporaryDirectory() as folder:
    path = Path(folder) / "values.npy"
    np.save(path, np.arange(1000, dtype=np.float64))
    mapped = np.load(path, mmap_mode="r",
                allow_pickle=False)
    first_chunk_mean = mapped[:100].mean()
    print("Mapped type:", type(mapped).__name__)
    print("First chunk mean:", first_chunk_mean)
    del mapped  # release before cleanup on Windows

Mapped type: memmap
First chunk mean: 49.5

File-backed storage

mmap_mode="r" maps the file read-only instead of loading it all.

Slices read what they need

mapped[:100] touches only the first 100 values.

Release the mapping

del mapped before the temporary folder is cleaned up.

Nothing is read in bulk up front; when we take mapped[:100] and its mean, only that part of the file is needed, and the mean of 0 to 99 is 49.5. allow_pickle=False is a safety habit for loading files. 9

Picture the file as ten blocks of 100 values each. A memory map gives you an array that covers all of them, but the operating system only reads the parts you actually touch. Taking mapped[:100] reads the orange block, and its mean is 49.5. This is how NumPy can work with files larger than your RAM. The catch is in the third card: operations still allocate full-size outputs, so mapped * 2 on a huge file would try to build a huge in-memory array. When data is large, process it slice by slice. Try it: loop over ten chunks of 100, collect each chunk's mean, and average them. Because all chunks are the same size, the average of the chunk means equals the full-array mean, 499.5.

The idea to remember

Slices share.
Copy on purpose.

A basic slice is a view of the same buffer. Call .copy() when you need independent data, and check with np.shares_memory.

Pause here. Views are a feature, not a bug: they make slicing, transposing and reshaping almost free, because no data moves. The price is that a write through a view reaches the original. When you need data that can change independently, make the copy explicit, and when you are unsure, ask np.shares_memory instead of guessing.
