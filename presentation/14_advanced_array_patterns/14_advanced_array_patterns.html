Step 1 · Einsum names the axes

Label axes; repeated ones sum

One letter per axis

"ij" means A has two axes, called i and j.

Missing from output: summed

In ij,jk->ik, j disappears, so it is summed over.

Check against the familiar

The asserts compare with A @ B and (A * A).sum(axis=1).

A = np.arange(6, dtype=float).reshape(2, 3)
B = np.arange(12, dtype=float).reshape(3, 4)
product = np.einsum("ij,jk->ik", A, B,
                    optimize=True)
row_energy = np.einsum("ij,ij->i", A, A)
print(product)
print("Row energy:", row_energy)
np.testing.assert_allclose(product, A @ B)

[[20. 23. 26. 29.]
 [56. 68. 80. 92.]]
Row energy: [ 5. 50.]

3

np.einsum takes a subscript string and the arrays. Each input gets one letter per axis; the part after the arrow lists the axes the output keeps. A letter that appears in the inputs but not in the output is summed over, after multiplying matching elements. So ij,jk->ik is the matrix product, and ij,ij->i multiplies A by itself elementwise and sums each row, giving the row energies 5 and 50. Always write the explicit output after the arrow and test against an operation you already trust. optimize=True lets NumPy choose an efficient contraction order. Try it: the dot product of two 1D arrays is np.einsum("i,i->", a, b), and the trace of a square matrix is np.einsum("ii->", M).

4

Map each letter to an axis length. In A, i has length 2 and j has length 3; in B, j has length 3 and k has length 4. The shared letter j must have the same length in both, just like the inner dimensions of a matrix product. The output keeps i and k, so its shape is (2, 4). Each output element multiplies along j and adds: for product[0, 0], the blue row of A, 0, 1, 2, meets the blue column of B, 0, 4, 8, giving 0 + 4 + 16 = 20, the first value the notebook printed. Changing the output letters changes the operation: ij,jk->ki would give the transposed product, and ij,jk-> with nothing after the arrow would sum everything to one number.

Step 2 · Rolling windows as views

Overlapping windows, no copies

from numpy.lib.stride_tricks import sliding_window_view
signal = np.array([1., 2., 3., 4., 5., 6.])
windows = sliding_window_view(signal, window_shape=3)
rolling_mean = windows.mean(axis=-1)
print(windows)
print("Rolling means:", rolling_mean)
assert not windows.flags.writeable
assert np.shares_memory(signal, windows)

[[1. 2. 3.]
 [2. 3. 4.]
 [3. 4. 5.]
 [4. 5. 6.]]
Rolling means: [2. 3. 4. 5.]

n − w + 1 windows

6 values, width 3: shape (4, 3).

A read-only view

It shares memory with signal; windows overlap, so writes are blocked.

Reduce the last axis

mean(axis=-1) gives one value per window.

NumPy course · 14 Advanced array patterns

5

sliding_window_view returns a new array whose last axis runs along each window. A window of width w over n values gives n - w + 1 complete windows, here 6 - 3 + 1 = 4, so the shape is (4, 3). It is a view built with strides, as in notebook 11: no window is copied, which the shares_memory assert confirms. Because the windows overlap, one element appears in several windows, so NumPy makes the view read-only to stop a write from changing several windows at once. Reducing still touches every window entry, so for long rolling sums a cumulative-sum trick can be cheaper. Try it: compute windows.min(axis=-1) and windows.max(axis=-1), giving [1, 2, 3, 4] and [3, 4, 5, 6]; each result belongs at the last index of its window, positions 2 to 5 of signal.

Step 3 · Repeated indices

+= can miss repeated indices

a[index] += value is buffered

A repeated position may be updated only once.

np.add.at is unbuffered

It applies every occurrence, one at a time.

bincount for integer codes

With weights=values it gives the same sums, often faster.

indices = np.array([0, 0, 2])
values = np.array([1., 1., 5.])
buffered = np.zeros(3)
buffered[indices] += values
accumulated = np.zeros(3)
np.add.at(accumulated, indices, values)
print("Buffered:", buffered)
print("Accumulated:", accumulated)

Buffered: [1. 0. 5.]
Accumulated: [2. 0. 5.]

NumPy course · 14 Advanced array patterns

7

Fancy-index assignment with += is shorthand for: read buffered[indices], add values, write the result back to buffered[indices]. The read happens once for all indices, so both occurrences of index 0 read the original 0 and add 1, and the second write simply overwrites the first. The result at position 0 is 1, not 2: an update is silently lost. np.add.at is the unbuffered version of the same ufunc and applies each occurrence in turn, giving 2. For sums over nonnegative integer codes, np.bincount(indices, weights=values, minlength=3) is a simpler and often faster equivalent, and the notebook asserts that it matches. Try it: use np.maximum.at(out, groups, values) with out starting as np.full(number_of_groups, -np.inf) to get the largest value per group.

8

Here the three updates are drawn as chips: two of them, outlined in orange, target the same position 0. With buffered fancy indexing, NumPy gathers buffered[[0, 0, 2]] into a temporary array, [0, 0, 0], adds [1, 1, 5] to get [1, 1, 5], and scatters the result back. Position 0 is written twice with the value 1, so the final array is [1, 0, 5]: one of the two increments is lost, and no error is raised. np.add.at does the addition in place for each occurrence, so position 0 goes 0, then 1, then 2, giving [2, 0, 5]. This matters for histograms, group sums and scatter operations, where repeated indices are the normal case, not the exception.

The idea to remember

Name the axes.
View, don't copy.
Count every repeat.

einsum says which axes survive and which are summed; windows are views; np.add.at applies every repeated index.

Pause here. The three tools share a theme: say precisely what you mean, and NumPy does the work without hidden surprises. einsum makes every axis explicit, so a contraction reads like its formula. sliding_window_view reuses memory instead of copying overlapping data. np.add.at removes the silent data loss of buffered fancy-index updates. In each case the notebook verified the new tool against a familiar one, and that habit is the real lesson.

11

The challenge has no supplied check: write your own. A Gram matrix of a 3 × 2 matrix X is X transposed times X, which is 2 × 2. For a batch, swapaxes(-1, -2) transposes only the last two axes, and @ broadcasts over the leading batch axis, so the result has shape (4, 2, 2). The einsum version names every axis: "bij,bik->bjk" keeps the batch axis b, sums over the shared row axis i, and keeps j and k. Compare the two with np.testing.assert_allclose. Each Gram matrix should also be symmetric, which is a second check worth adding. Then restart the kernel and run all cells.
