Welcome to notebook 12. Vectorization means moving repeated numeric work out of Python loops and into array operations that run in compiled code. It is often dramatically faster, but this notebook teaches the discipline around it: prove the fast version is correct, measure speed fairly instead of assuming it, and keep an eye on the temporary arrays that vectorized expressions create. Step 1 · Correctness before timing

Same answer first, speed second

def squared_distance_loop(a, b):
    total = 0.0
    for i in range(len(a)):
        total += (a[i] - b[i]) ** 2
    return total

def squared_distance_numpy(a, b):
    return np.sum((a - b) ** 2)

The loop is the clear reference. np.vectorize only wraps Python calls: it is not a speed-up.

rng = np.random.default_rng(4)
a, b = rng.normal(size=(2, 20_000))
np.testing.assert_allclose(squared_distance_loop(a, b), squared_distance_numpy(a, b))
print("Agreement checked.")

Agreement checked.

3

Both functions compute the squared distance between two vectors: subtract, square, and add up. The loop version does it one element at a time in Python, which makes it easy to read and easy to trust. The NumPy version does the same maths as one array expression that runs in compiled code. Before timing anything, the notebook generates 20,000 random pairs with a seeded generator and checks that both versions agree with assert_allclose, which tolerates tiny floating-point differences in summation order. A word on np.vectorize: it makes a Python function accept arrays, but internally it still calls that function once per element, so it is a convenience, not a performance tool. Try it: check both functions on equal vectors, where the answer must be 0.0, and on one-element vectors.

Step 2 · Benchmark repeated runs

Time it fairly, more than once

from timeit import repeat
loop_seconds = min(repeat(lambda: squared_distance_loop(a, b), number=3, repeat=3)) / 3
numpy_seconds = min(repeat(lambda: squared_distance_numpy(a, b), number=3, repeat=3)) / 3
print(f"Python loop: {loop_seconds:.6f} seconds/call")
print(f"NumPy:       {numpy_seconds:.6f} seconds/call")
print(f"Observed ratio: {loop_seconds / numpy_seconds:.1f}x")
print("Input shape/dtype:", a.shape, a.dtype)

Python loop: 0.006254 seconds/call
NumPy:       0.000018 seconds/call
Observed ratio: 350.0x
Input shape/dtype: (20000,) float64

4

timeit.repeat runs each function three times per measurement and repeats the measurement three times on the same inputs. Taking the minimum approximates the least interrupted run, because background activity can only make a run slower, never faster. Dividing by number=3 gives seconds per call. The report includes the input shape and dtype, since a timing without its setup is hard to interpret. Note what the cell does not do: it never asserts that NumPy is faster. Hardware, dtype, memory layout and the library build all change the numbers, so speed is reported, not tested. Try it: repeat the benchmark for 10 values and for 100,000 values. Do not assume the same ratio: for tiny arrays the fixed overhead of each NumPy call dominates, so the advantage shrinks or can even reverse.

NumPy course · 12 Vectorization

6

Array expressions are convenient, but each intermediate result is a brand-new array. In np.sum((a - b) ** 2), the subtraction allocates one full-size temporary, shown dashed, and squaring allocates another. Ufuncs such as np.subtract and np.square accept an out= argument that writes the result into an array you already own. Here scratch is allocated once with np.empty_like, filled by subtract, then squared in place. The notebook prints its size: 20,000 float64 values times 8 bytes is 160000 bytes. For small arrays this barely matters; for arrays of gigabytes, avoiding extra temporaries can decide whether the code runs at all. Try it: explain why calling np.append inside a loop is slow. Arrays cannot grow in place, so every append allocates a new, larger array and copies all the old data into it, which makes the loop quadratic in total copying.

Step 3 · Process chunks

Chunking caps the temporaries

chunk_result = 0.0
chunk_size = 2048
for start in range(0, a.size, chunk_size):
    difference = (a[start:start + chunk_size]
                  - b[start:start + chunk_size])
    chunk_result += np.sum(difference ** 2)
np.testing.assert_allclose(buffer_result, chunk_result)
print("One chunk difference bytes (maximum):",
      chunk_size * a.itemsize)

One chunk difference bytes (maximum): 16384

Fixed-size pieces

Each pass handles at most 2048 values of a and b.

Small temporaries

difference never exceeds 2048 × 8 bytes.

Same answer

The sum of chunk results matches the buffer result within tolerance.

NumPy course · 12 Vectorization

7

Chunking is the other tool for limiting memory. Instead of one expression over all 20,000 values, the loop walks the arrays in slices of 2048. Inside each pass, a vectorized expression still does the real work, so we keep most of the speed while the temporary difference array never holds more than 2048 values. The loop is a Python loop, but it runs only about ten times instead of 20,000. The final slice is simply shorter: slicing past the end of an array is allowed and stops at the last element. Adding chunk sums changes the order of floating-point additions, so the result can differ from the full sum in the last digits, which is why the check uses assert_allclose rather than exact equality. The printed maximum temporary is 2048 times 8 bytes, 16384 bytes.

The idea to remember

Check first.
Then measure.

Vectorize against a slow reference, time repeated runs, and watch the temporary arrays your expressions create.

Pause here. A fast wrong answer is worthless, and a speed claim without a measurement is a guess. Keep a simple reference implementation, prove agreement with assert_allclose, benchmark with repeated runs and report the setup, and remember that every intermediate array costs memory. Reuse buffers with out= or process chunks when the data gets large.
