Step 1 · Meaningful tolerances

0.1 + 0.2 is not exactly 0.3

No exact binary form

0.1, 0.2 and 0.3 are each stored as the nearest binary fraction.

== demands identical bits

The rounding errors do not cancel, so it says False.

Tolerances ask "close enough?"

rtol scales with the values; atol matters near zero.

value = 0.1 + 0.2
print("Stored sum:", repr(value))
print("Exact equality:", value == 0.3)
print("Close:", np.isclose(value, 0.3,
      rtol=1e-12, atol=1e-15))
np.testing.assert_allclose(value, 0.3,
    rtol=1e-12, atol=1e-15)

Many decimal fractions, such as 0.1, have no exact binary representation, so the computer stores the closest value it can. The tiny errors in 0.1 and 0.2 add up to a sum that is not the same double as 0.3, so exact equality fails. np.isclose and np.testing.assert_allclose pass when the difference is at most atol plus rtol times the size of the expected value. Choose the tolerances from the scale and accuracy your problem needs; the defaults are not a universal rule. Try it: compare 1e-12 and 0. With the default atol of 1e-8, np.isclose(1e-12, 0) is True; with atol=0 it is False, because a relative tolerance times zero is zero. Near zero, only the absolute tolerance can help.

This slide shows why exact equality is the wrong question. Python prints the shortest decimal that identifies each double: 0.3 prints as 0.3, but the sum needs seventeen decimals, ending in a 4, so the two are different numbers. The tolerance test instead asks whether the gap is no larger than atol plus rtol times the expected value, which in this example is about 3e-13, far larger than the gap. Machine epsilon, printed by np.finfo, is the spacing between 1 and the next representable number: about 1e-7 for float32 and 2e-16 for float64, roughly 7 and 16 significant digits. Pick rtol a little above the precision your computation can actually deliver.

Tiny changes vanish in 1 + x

print("Naive log:", np.log(1 + tiny))

print("Naive exp change:", np.exp(tiny) - 1)

1 + 1e-16 rounds to 1.0

It is below float64 epsilon, so the change is lost before log runs.

log1p(x) is log(1 + x)

Computed without ever forming 1 + x.

Avoids subtracting two nearly equal numbers.

5

Cancellation happens when you subtract nearly equal numbers, or add a tiny number to a large one: the meaningful digits fall off the end of the 53-bit significand. Here 1 + 1e-16 is stored as exactly 1.0, so log gives 0 and exp(tiny) - 1 gives 0, even though the true answers are about 1e-16. np.log1p and np.expm1 are written to work on x directly, so they return 1e-16, accurate to full precision. Use them whenever x can be small, for example in log returns, interest rates or probabilities near zero. Try it: find a value for which float32 rounds 1 + x back to 1 while float64 does not. x = 1e-8 works: np.float32(1) + np.float32(1e-8) equals 1, because float32 epsilon is about 1.2e-7, while 1 + 1e-8 in float64 is still larger than 1.

NumPy course · 13 Numerical stability

6

NumPy integers have a fixed width. An int8 has 8 bits, so it holds 256 values, from -128 to 127. The bar shows that range: starting at 120 (blue), adding 120 runs past 127, wraps around to -128 and keeps counting until it lands on -16 (orange), which is 240 minus 256. NumPy array arithmetic does not raise an error for this; it silently wraps. The fix is to promote the dtype before the arithmetic that might overflow: with int64 the sum is 240. Watch for this with small dtypes such as int8, uint8 image pixels or int16 sensor data, especially when summing or multiplying.

Step 3 · Stable softmax

Subtract the max, then exp

def softmax(scores):
    scores = np.asarray(scores, dtype=np.float64)
    shifted = scores - scores.max(axis=-1, keepdims=True)
    exponentials = np.exp(shifted)
    return exponentials / exponentials.sum(
        axis=-1, keepdims=True)

scores = np.array([[1000., 1001., 1002.],
                   [-1000., -1000., -999.]])
probabilities = softmax(scores)
print(probabilities)

[[0.09   0.2447 0.6652]
 [0.2119 0.2119 0.5761]]

Scores to weights

Positive values that sum to one along each row.

Shift is free

softmax(scores + 500) gives the same result.

keepdims=True

Keeps the row axis so each max broadcasts.

7

Softmax turns any finite scores into positive weights that sum to one: exponentiate each score, then divide by the row total. Exponentials grow fast, so scores near 1000 overflow float64. Subtracting the row maximum first changes nothing mathematically, because the same factor cancels in the numerator and denominator, but now the largest exponent is exp(0) = 1. The notebook's asserts confirm that every value is finite, each row sums to 1, and shifting all scores by 500 gives the same probabilities. Very negative shifted scores can still underflow to 0, which is usually harmless. Try it: add a test for equal scores, which should give equal weights such as [1/3, 1/3, 1/3], and one for a row with a single score, which should give [1.0].

8

Follow the first row of the example, [1000, 1001, 1002], through both versions. Naively, np.exp(1000) is far beyond the largest float64, about 1.8e308, so NumPy returns inf with an overflow warning; dividing inf by inf gives nan, and every weight is lost. The stable version subtracts the row maximum, 1002, first, giving [-2, -1, 0]. Their exponentials are about 0.1353, 0.3679 and 1, all safe, and dividing by their sum gives exactly the notebook's output, 0.09, 0.2447 and 0.6652. The shift cancels out mathematically, so the result is the true softmax. The same trick appears as log-sum-exp in statistics and machine learning.

The idea to remember

Compare with tolerance.
Compute in a safe range.

Floats are approximations with fixed limits. Test closeness, keep small changes, and shift or promote before values overflow.

Pause here. Every result in this notebook comes from one fact: a number is stored in a fixed number of bits. That is why == fails on 0.1 + 0.2, why 1 + 1e-16 is 1, why int8 wraps, and why exp(1000) overflows. The remedies follow the same pattern: compare with explicit tolerances, use functions like log1p and expm1 that avoid cancellation, promote to a wider dtype, and rearrange formulas, like subtracting the maximum in softmax, so intermediate values stay in range.

With float32 accumulation, small values added to a large running total can be rounded away, because float32 keeps only about 7 significant digits; passing dtype=np.float64 to sum accumulates in double precision and keeps them.
